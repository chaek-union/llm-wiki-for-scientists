# 25장. Notion MCP로 연구실 프로젝트 관리하기

저희 연구실의 Notion을 열면 연구과제마다 별도의 데이터베이스가 보인다. 학생과 공동연구자는 자신이 참여하는 과제에 들어가 실험 기록, 분석 결과, 미팅 노트, 논문 계획을 함께 갱신한다. 지도교수는 여러 과제의 진행 상황을 같은 형식으로 훑고, 확인이 필요한 카드만 골라 의견을 남긴다. 연구실 전체가 알아야 하는 대학원 과정, 랩미팅, 논문 작성법, 서버 사용법, 연구 행정 담당자 정보는 별도의 연구실 공통 데이터베이스에 모은다.

이 장에서 소개하는 구조는 저희 연구실이 실제로 쓰는 Notion을 바탕으로 정리했다. 공개 글에 연구 대상과 구성원의 이름을 노출하지 않기 위해 과제명은 가상으로 바꾸었다. 예시로 사용할 `면역세포 지도 과제`는 실제 과제가 아니지만, 데이터베이스의 보기와 속성, 카드 종류, 미팅 기록 방식은 현재 운영 구조를 반영한다. 독자는 이 구성 방법을 자기 과제명과 연구 갈래에 맞춰 적용하면 된다.

# 유료 Notion을 운영 비용에 포함하기

저희 연구실은 Notion 유료 버전을 사용한다. 여러 학생과 공동연구자가 과제별 권한을 나누어 쓰고, Notion MCP를 연구실 운영에 연결하기 위해서다. 이 장의 절차를 그대로 적용하려면 유료 구독을 운영 비용에 포함해야 한다. 도입 예산에는 구성원 수에 따른 구독료와 연결할 MCP 서비스의 이용 조건도 함께 계산한다.

Notion MCP는 코덱스와 Claude Code를 비롯한 MCP 지원 에이전트가 사용자의 Notion 페이지를 읽고 갱신하도록 연결한다. 코덱스에서 MCP 서버를 연결하는 방법은 [OpenAI MCP 공식 문서](https://developers.openai.com/codex/extend/mcp)에서 볼 수 있다. 에이전트가 볼 수 있는 범위는 연결한 사람의 기존 Notion 권한을 따른다. 외부 공동연구자를 특정 과제에만 초대했다면, 그 사람은 다른 과제 데이터베이스나 연구실 내부 문서를 볼 수 없다. Notion의 연결 방법과 지원 기능은 [Notion MCP 공식 안내](https://www.notion.com/help/notion-mcp)에서 확인할 수 있다. Notion의 요금제와 AI·통합 기능 범위는 바뀔 수 있으므로 실제 도입 시점에는 [요금제 공식 안내](https://www.notion.com/help/upgrade-or-downgrade-your-plan)도 함께 확인한다.

유료 계정을 준비한 뒤에는 권한부터 정한다. 학생은 자기 과제의 카드를 작성하고, 공동연구자는 공유받은 과제만 열며, 지도교수와 과제 관리자는 전체 진행 상황을 확인한다. 에이전트도 같은 권한 안에서 작동한다. 이 원칙을 지키면 MCP를 연결해도 새로운 공개 범위가 생기지 않는다.

# 과제 하나에 데이터베이스 하나

저희 연구실은 연구과제를 Notion 운영의 기본 단위로 삼는다. 과제가 시작되면 전용 데이터베이스를 만들고 참여자를 초대한다. 과제 데이터베이스에는 연구계획, 데이터, 분석, 문헌, 미팅, 논문, 행정 기록이 함께 들어간다. 구성원은 한 과제의 현재 상태를 확인하기 위해 여러 서비스와 개인 노트를 돌아다닐 필요가 없다.

데이터베이스에는 보통 세 가지 보기를 만든다.

| 보기 | 용도 |
|---|---|
| Workstream 보드 | 세부 연구 갈래별로 카드를 나누어 진행 상황을 본다 |
| 전체 표 | 담당자, 기한, 문서유형, 상태를 한꺼번에 확인한다 |
| 타임라인 | 마일스톤, 분석 일정, 원고 작성 일정을 시간순으로 본다 |

가상의 `면역세포 지도 과제`를 예로 들면 Workstream은 `코호트`, `샘플 처리`, `단일세포 분석`, `기능 검증`, `논문 작성`으로 나눌 수 있다. 각 열에는 그 연구 갈래에서 실제로 쓰는 카드가 놓인다. 학생은 자신의 분석 카드를 갱신하고, 지도교수는 보드 전체를 보며 막힌 작업과 다음 결정을 확인한다.

# 프로젝트 보드에 만드는 카드

프로젝트마다 연구 내용은 달라도 자주 쓰는 문서의 종류는 비슷하다. 저희 연구실에서는 다음과 같은 카드를 만든다.

| 문서유형 | 카드에 담는 내용 | 가상 예시 |
|---|---|---|
| Project map(프로젝트 지도) | 연구 질문, 세부 과제, 참여자, 주요 일정, 산출물 | 면역세포 지도 과제 개요 |
| Data hub(데이터 허브) | 데이터 위치, 판본, 접근 조건, 담당자 | 단일세포 데이터 현황 |
| Sample inventory(샘플 목록) | 샘플 수, 처리 상태, 제외 사유, 품질 확인 | 1차 코호트 샘플 목록 |
| Pipeline provenance(분석 이력) | 입력 자료, 코드 판본, 실행 조건, 출력물 | 세포 유형 분류 파이프라인 |
| Analysis result(분석 결과) | 질문, 방법, 그림, 해석, 다음 분석 | 치료 반응군 비교 결과 |
| Manuscript plan(논문 계획) | 논문 메시지, 그림 구성, 집필 담당, 목표 일정 | 면역세포 지도 원고 계획 |
| Literature note(문헌 노트) | 논문 요약, 과제 관련성, 주의점, 다음 행동 | 세포 상태 전이 참고 논문 |
| Meeting note(미팅 노트) | 논의 자료, 결정, 할 일, 담당자, 기한 | 세부 분석팀 미팅 |
| Logistics(행정·운영) | 구매, 협약, 자료 이전, 보고 일정 | 2차년도 보고 준비 |
| Needs review(확인 필요) | 지도교수나 공동연구자의 판단이 필요한 항목 | 샘플 제외 기준 확인 |
| Archive(보관) | 종료되었고 검색을 위해 남기는 기록 | 종료된 예비 분석 |

카드는 처음부터 완성된 보고서로 만들지 않는다. 분석을 시작할 때 질문과 입력 자료를 적고, 결과가 나오면 그림과 해석을 추가한다. 논의가 끝난 뒤에는 결정과 다음 행동을 남긴다. 한 카드가 작업의 진행 기록과 미팅 자료를 함께 제공하므로, 지난주에 어떤 판단이 바뀌었는지 쉽게 확인할 수 있다.

# 공동 랩노트와 진도 관리

분석 결과 카드는 공동 랩노트로 쓴다. 학생이 개인 컴퓨터에만 적어 둔 분석 메모는 지도교수와 공동연구자가 볼 수 없고, 다음 미팅에서 설명을 처음부터 다시 해야 한다. 과제 데이터베이스의 카드에 기록하면 참여자가 같은 그림과 같은 설명을 보며 의견을 남길 수 있다. 댓글과 멘션으로 받은 피드백도 카드에 남기므로 다음 분석에서 판단의 근거를 다시 확인할 수 있다.

분석 카드는 다음 항목으로 구성한다.

1. 연구 질문과 이번 분석의 목적
2. 분석 날짜와 입력 데이터 판본
3. 사용한 방법, 코드, 주요 설정
4. 결과 그림과 표
5. 현재 해석과 남은 의문
6. 오류, 품질 문제, 막힌 지점
7. 다음 작업, 담당자, 기한

원시 데이터와 큰 중간 파일은 연구실 서버나 과제 폴더에 보관한다. Notion 카드에는 구성원이 결과를 이해하고 파일을 찾을 수 있는 설명과 링크를 둔다. 데이터 판본과 코드 실행 조건을 함께 적으면, 몇 달 뒤 결과를 다시 만들 때도 당시의 입력과 방법을 복원할 수 있다.

진행상태는 `Active`, `Waiting`, `Completed`, `Published`, `Needs confirmation`, `Archive`처럼 선택형 값으로 관리한다. `Waiting`에는 시퀀싱 결과 대기, 공동연구자 답변 대기, 데이터 사용 승인 대기처럼 작업이 멈춘 이유를 적는다. `Needs confirmation`은 샘플 제외, 분석 방향 변경, 외부 공유처럼 책임자의 판단이 필요한 카드에 붙인다. 지도교수는 이 두 상태를 우선 확인하면 된다.

# 카드 속성을 통일하기

과제가 늘어나면 같은 질문을 여러 데이터베이스에 해야 한다. 이번 달 마감은 무엇인지, 특정 학생이 맡은 작업은 몇 개인지, 원고로 이어진 분석은 어디까지 왔는지 확인하려면 속성 이름이 같아야 한다. 저희 연구실의 과제 보드는 다음 속성을 공통으로 쓴다.

| 속성 | 기록하는 내용 |
|---|---|
| 이름 | 카드 제목 |
| Workstream | 세부 연구 갈래 |
| 문서유형 | 프로젝트 지도, 분석 결과, 문헌 노트, 미팅 노트 등의 구분 |
| 진행상태 | Active, Waiting, Completed 등의 현재 상태 |
| 담당자 | 결과와 다음 행동을 책임지는 사람 |
| 기한 | 다음 확인일 또는 마감일 |
| 관련 원고·메모 | 이어지는 원고, 분석, 결정 기록 |
| 대표 페이지 | Workstream에서 먼저 읽어야 하는 기준 문서 |

모든 카드에 모든 속성을 채울 필요는 없다. 미팅 노트에는 날짜와 참석자, 분석 결과에는 입력 데이터 판본과 관련 원고가 더 중요하다. 공통 속성의 이름을 유지하면 에이전트가 여러 과제를 조회할 때 같은 방식으로 상태를 읽을 수 있다.

# LLM 위키에서 프로젝트 Notion으로 논문 공유하기

LLM 위키에 논문이 ingest되면 에이전트는 새 문헌의 제목, 초록, 주요 결과, 태그와 기존 위키 연결을 읽는다. 이어서 연구실의 과제 목록과 참여자 역할을 확인하고, 이 논문을 함께 읽어야 할 학생과 공동연구자를 고른다. 관련성이 확인된 논문은 해당 과제의 `참고 논문 및 아이디어` 페이지에 문헌 노트로 등록한다. 공유 대상은 그 논문의 방법이나 결과를 실제로 검토해야 하는 구성원으로 정한다.

이 과정은 다음 순서로 진행한다.

1. 새로 ingest된 논문의 서지정보와 위키 요약을 읽는다.
2. 논문의 질환, 데이터 유형, 분석 방법, 주요 결과를 현재 과제의 Workstream과 대조한다.
3. 관련 과제와 담당 학생, 공동연구자를 제안한다.
4. 과제별 문헌 노트 초안을 만든다.
5. 담당자가 관련성과 공개 범위를 확인한다.
6. Notion MCP로 과제 데이터베이스에 페이지를 만들고 읽을 사람을 알린다.

문헌 노트에는 다음 내용을 넣는다.

| 항목 | 내용 |
|---|---|
| 논문 정보 | 제목, 저자, 저널, 연도, DOI, 공개 주소 |
| 한 줄 요약 | 논문이 보여 준 결과 |
| 방법 | 자료와 분석 방법의 특징 |
| 주요 결과 | 현재 과제와 직접 관련된 결과 |
| 프로젝트 관련성 | 어느 Workstream의 어떤 판단에 도움이 되는지 |
| 주의점 | 표본, 방법, 해석의 제한 |
| 다음 행동 | 재현, 비교, 토론, 추가 문헌 확인 등의 후속 작업 |

같은 논문이 여러 과제와 관련될 때는 각 과제에 짧은 문헌 노트를 만든다. 예를 들어 한 과제에서는 세포 분류 방법을 검토하는 자료로 쓰고, 다른 과제에서는 코호트 구성을 비교하는 자료로 쓸 수 있다. LLM 위키의 원문 기반 요약은 한 번 유지하고, Notion에는 각 프로젝트에서 필요한 해석과 행동을 적는다. 과제별 접근 권한도 그대로 적용된다.


# 미팅 기록을 세 종류로 나누기

과제별 미팅은 성격에 따라 `총괄 미팅`, `세부 미팅`, `비정기 미팅`으로 나눈다. 한 페이지 안에서 제목을 구분해 모으거나, 미팅 데이터베이스의 유형 속성으로 필터링할 수 있다.

| 미팅 종류 | 참여자와 목적 | 가상 예시 |
|---|---|---|
| 총괄 미팅 | 세부 과제 책임자와 주요 참여자가 전체 진도, 예산, 산출물, 위험 요소를 확인한다 | 분기 총괄 미팅 |
| 세부 미팅 | 특정 Workstream 참여자가 실험과 분석 결과를 검토하고 다음 작업을 정한다 | 단일세포 분석팀 미팅 |
| 비정기 미팅 | 오류, 신규 자료, 외부 요청처럼 즉시 판단할 사안을 다룬다 | 샘플 품질 기준 긴급 논의 |

미팅 노트의 제목은 날짜와 미팅 유형, 주제를 함께 적는다. `[26.08.12] 세부 분석팀 - 세포 유형 판정 기준`처럼 쓰면 검색 결과만 보고도 내용을 짐작할 수 있다. 본문에는 다음 항목을 둔다.

1. 일시와 참석자
2. 안건과 미리 공유한 자료
3. 새로 확인한 사실과 분석 결과
4. 논의에서 확정한 결정
5. 후속 행동, 담당자, 기한
6. 다음 미팅에서 확인할 질문

학생은 미팅 전에 관련 분석 카드를 연결한다. 미팅 중에는 결정을 중심으로 짧게 메모하고, 끝난 뒤 담당자와 기한을 채운다. 공유받은 사람은 발언 순서를 다시 읽지 않아도 무엇이 결정되었고 누가 다음 작업을 맡았는지 알 수 있다.

# Zoom MCP에서 Notion 미팅 노트까지

온라인 미팅이 끝난 뒤에는 Zoom MCP와 Notion MCP를 이어서 기록 시간을 줄인다. Zoom의 MCP 서버는 권한이 있는 계정의 회의 자료, 전사, 요약, 후속 항목을 에이전트가 활용할 수 있도록 지원한다. 사용 가능한 자료는 Zoom 계정의 라이선스, 녹화 설정, 회의 소유권과 접근 권한에 따라 달라진다. 현재 기능과 조건은 [Zoom MCP Server 공식 문서](https://developers.zoom.us/docs/mcp/zoom-mcp-server/)와 [Zoom MCP 연결 안내](https://developers.zoom.us/docs/mcp/servers/connect-to-zoom-mcp-servers/)에서 확인할 수 있다.

저희 연구실에서 사용하는 흐름은 다음과 같다.

1. 회의가 끝나면 에이전트가 Zoom MCP에서 전사, 회의 요약, 다음 행동, 녹화 주소를 가져온다.
2. 회의에 사용한 슬라이드와 연결된 Notion 분석 카드를 함께 읽는다.
3. 전사에서 사실, 해석, 결정, 후속 행동을 구분해 미팅 노트 초안을 만든다.
4. 결정마다 근거가 된 그림이나 문서 링크를 연결한다.
5. 후속 행동에 담당자와 기한을 붙인다.
6. Notion MCP로 해당 과제의 미팅 노트에 초안을 기록한다.
7. 참석자가 결정과 담당자를 확인한 뒤 공유 상태로 바꾼다.

Zoom 전사가 제공되지 않은 회의는 녹음 파일을 로컬 Whisper로 전사한 뒤 같은 절차를 적용할 수 있다. 어느 경로를 쓰든 원문 전사는 보존하고, 공유 노트에는 확인된 결정과 후속 행동을 정리한다. 전사에 없는 내용을 에이전트가 보충하지 않도록 회의 자료와 원문을 함께 확인한다.

# 연구실 전체가 함께 보는 공통 Notion

과제 데이터베이스와 별도로 연구실 공통 데이터베이스를 운영한다. 구성원이 바뀌어도 계속 참고해야 하는 규정, 절차, 연락처, 교육 자료를 모으는 곳이다. 저희 연구실에서는 다음 범주를 관리한다.

| 범주 | 기록 예시 |
|---|---|
| 대학원 과정 | 수강, 학위 요건, 자격시험, 연구윤리, 졸업 절차 |
| 랩미팅과 스터디 | 연간 일정, 발표 순서, 저널클럽, 교육 자료 |
| 논문 작성 | 원고 폴더 구성, 그림과 표, 참고문헌, 투고 점검표 |
| 컴퓨팅과 서버 | 계정 신청, GPU 사용, 저장 공간, 백업, 장애 대응 |
| 연구 행정 | 구매, 연구비, 과제 보고, 행정 담당자, 자주 쓰는 양식 |
| 연구실 운영 | 신규 구성원 안내, 공용 장비, 예약, 안전, 연락 체계 |
| AI 도구 | LLM 위키, MCP 연결, 에이전트 사용 규칙, 데이터 보안 |

새 학생이 들어오면 공통 Notion에서 대학원 과정과 서버 사용법을 찾는다. 과제에 합류하면 해당 과제 데이터베이스에서 프로젝트 지도, 대표 분석, 참고 논문, 최근 미팅 노트를 읽는다. 에이전트에게 질문할 때도 정보의 종류에 따라 조회할 곳이 정해진다.

| 질문 | 먼저 확인할 곳 |
|---|---|
| 이 논문이 무엇을 보고했는가 | LLM 위키 |
| 이 논문을 현재 과제에서 어떻게 쓸 것인가 | 과제별 Notion 문헌 노트 |
| 분석과 원고가 어디까지 진행됐는가 | 과제별 Notion 보드 |
| 연구실의 서버와 행정 절차는 무엇인가 | 연구실 공통 Notion |

이 구분 덕분에 에이전트는 문헌 근거, 프로젝트 진행 상황, 연구실 운영 규칙을 필요한 순서로 읽을 수 있다. LLM 위키에서 찾은 논문은 과제별 문헌 노트로 이어지고, 미팅에서 정한 작업은 분석 카드와 원고 계획에 연결된다. Notion MCP는 이 연결을 사람이 매번 복사해 옮기는 시간을 줄여 준다.

# 실제 운영 순서

한 주의 운영은 다음처럼 이어진다.

1. 학생이 분석 카드에 새 결과와 문제, 다음 작업을 기록한다.
2. 에이전트가 새로 ingest된 논문을 확인하고 관련 과제와 읽을 사람을 제안한다.
3. 담당자가 문헌 노트 초안을 확인하고 과제 Notion에 공유한다.
4. 미팅 전에 분석 카드와 문헌 노트를 안건에 연결한다.
5. 미팅 뒤 Zoom MCP의 전사와 자료를 이용해 노트 초안을 만든다.
6. 참석자가 결정, 담당자, 기한을 확인한다.
7. 확정된 후속 행동을 기존 분석 카드와 원고 계획에 연결한다.

이 과정이 반복되면 Notion 보드만 보아도 과제의 연구 질문, 최신 결과, 막힌 작업, 읽어야 할 논문, 최근 결정이 함께 보인다. 지도교수는 모든 세부 기록을 처음부터 읽지 않고 `Waiting`과 `Needs confirmation`을 먼저 확인할 수 있다. 학생과 공동연구자는 자신이 맡은 카드에서 다음 행동을 찾는다. LLM 위키와 Notion이 MCP로 연결되면서 논문을 읽은 결과가 실제 과제의 결정과 작업으로 이어진다.
